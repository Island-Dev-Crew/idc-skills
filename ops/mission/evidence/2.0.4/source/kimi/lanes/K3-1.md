Blind hypotheses (candidate seeds, ranked by prior):

1. **B1 → signer-file substitution.** `keys/allowed_signers` and `keys/idc-skills-signing.pub` live in-tree. If the manifest does NOT hash-cover `keys/` (or the verifier accepts a flag/env override of the signers path), replacing them with attacker material makes any attacker signature verify. Claimed mitigation is the `expectedSigningFingerprint` pin in policy.json — but that pin is itself in-tree, so it only helps if the verifier reads it from a signed/immovable location and the pin file is hash-covered. Seed: test flag override + manifest coverage of keys/ and policy.json.
2. **B2 → allowed_signers multi-line confusion.** ssh-keygen -Y verify accepts the signature if ANY principal line matches. Appending a second `idc-skills ssh-ed25519 <attacker>` line, duplicate principals, or wildcard principal (`*`) would let attacker-key signatures pass wherever the attacker can edit the file. (Boundary: needs tree edit — see B1 coverage question.)
3. **B3 → namespace/principal substitution.** Swap manifest.sig ↔ releases.json.sig ↔ tag signature across namespaces file/git/idc-skills-release-index-v1. Expect HELD (ssh-keygen namespaces are domain-separated), but the in-tree verifier scripts may pass the wrong `-n` value or skip `-I` principal check — must read scripts to confirm they pin both.
4. **B4 → canonicalization gap.** If the verifier re-serializes parsed JSON before hashing (or compares parsed fields instead of raw bytes), then signed-but-noncanonical bytes (duplicate keys, reordered keys, unicode escapes, big ints, NaN) could let two byte-strings with the same parsed content diverge between signer view and verifier view. Python's json accepts NaN/Infinity and duplicate keys silently. Seed: read scripts/skill_integrity.py to find raw-hash vs re-serialize.
5. **B5 → manifest closure gaps.** Manifest is a file→sha256 list. Classic gaps: untracked extra files not flagged, path traversal entries (`../`), absolute paths, case aliases, symlink entries, unicode NFC/NFD alias paths, files listed but with mode drift. If manifest omits `scripts/`, `bootstrap/`, `keys/`, or `integrity/policy.json`, the verifier itself is attacker-editable.
6. **B6 → TOCTOU.** pretooluse-skill-integrity.py likely verifies-then-allows; if hashing happens at a different time than signature verification, or results are cached by mtime/size, a swap between verify and execution passes.
7. **B7 → readyToRun authority flip.** Tree claims authority:"content-only". Grep for readyToRun / env / config paths that emit readyToRun=true from in-tree (attacker-editable) data.
8. **B8 → index/manifest cross-replay.** Old signed manifest+sig presented against current tree (rollback), or 2.0.2-era artifacts replayed. Depends on whether the verifier checks manifestSequence/version pinning or just "some valid signature over some manifest".
9. **B9 → JSON parser differential on policy.json.** Policy drives deny-exceptions and control-files list. If parser accepts duplicate keys, attacker who can touch policy.json (in-tree!) adds exceptions silently. Severity gated by B5 coverage of policy.json.

### K3-1-C6 — Canonical JSON attacks on manifest/policy/index parsers
- **Status: HELD** (one inert parser differential noted) · Severity: n/a — sub-note FALSE-POSITIVE/Ignore
- Design (verified by reading + tests): signature is verified over the **raw captured bytes**, then those same bytes are parsed and must satisfy `data == canonical_bytes(parsed)` (`skill_integrity.py:1010`, launcher `load_canonical_json:90-107`). Both directions of the classic canonicalization gap are closed: nothing is re-serialized before hashing, and non-canonical signed bytes are rejected outright.
- In-tree parser battery (`_load_canonical_manifest_bytes`): duplicate top-level key bytes → rejected ("not canonical"); genuinely reordered key bytes → rejected; unicode-escape alias (`v\u0076`) → rejected; `skillCount:true` (bool-as-int) → rejected (`type(x) is not int`); `manifestSequence=2**80` → rejected (≤2^53−1); trailing data → rejected; unknown top-level key → rejected (exact key set); `posixMode=0o7777` / negative size / float size → rejected per-record; invalid UTF-8 → rejected; >64 MiB → rejected by `MAX_MANIFEST_BYTES` (code-level, `:46`).
- Launcher parser additionally rejects duplicate keys (`object_pairs_hook`) and non-finite numbers (`parse_constant`) — strict superset.
- Sub-note (FALSE-POSITIVE, severity Ignore): the in-tree parser lacks a `parse_constant` hook, so `NaN` parses and round-trips canonically in fields that are never semantically compared (e.g. `remoteObservations`). Unreachable without the signing key; even a signer-produced NaN there is never consumed by any check (compare set at `:1138-1148` excludes it; `NaN != NaN` would fail any equality anyway). No boundary crossed. Remediation direction (optional hardening): add `parse_constant` rejection to match the launcher.
- policy.json / registry.json parsers (`_load_json`) accept duplicate keys last-wins, but both files are hash-bound by the signed manifest, so parser leniency is not attacker-reachable (C2 covers edit attempts).
- Evidence: `evidence/K3-1-o6-canonical/evidence.txt`.
