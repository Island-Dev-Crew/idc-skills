## Candidates

### K3-3-C1 — PreToolUse hook does not bind POSIX mode (or xattrs) of installed skill bytes
- Verdict: CONFIRMED
- Severity: Low
- Layers: 1 (installed-target verification scope inside the execution gate)
- Reachability: any same-user process can `chmod 644` an installed helper script after install; the gate still authorizes.
- Evidence: evidence/K3-3-E7/summary.txt. `chmod 644 .../agent-guardrails/scripts/deny-dangerous.sh` (canonical 755, identical bytes) → `install.py --verify-only` reports `status=drift changed:scripts/deny-dangerous.sh`, but `pretooluse-skill-integrity.py` prints `SKILL CONTENT VERIFIED 5/5` exit 0. Root cause: `skill_integrity.verify_skill_directory` compares `{sha256, size}` records only, and the signed manifest's skill file records carry no `posixMode` (unlike `repositoryFiles`). xattr probe (`os.setxattr user.inert`) is invisible to BOTH layers — comparison scope is bytes+symlink-targets+mode only.
- Impact: bounded — byte content is still bound; stripping an exec bit degrades (fail-closed-ish) rather than escalates; adding an exec bit to a same-bytes file is harness-interpretation dependent. But the hook docstring claims "the bytes the harness will execute" must match; the *closure* it compares is narrower than the installer's own `tree_manifest`.
- Recommendation: include `posixMode` in signed skill file records and compare it in `verify_skill_directory`; document xattr exclusion explicitly.

### K3-3-C2 — Hook verifies only the first-found skill field; disagreeing payload fields are not cross-checked
- Verdict: CONFIRMED (mechanic) / THEORETICAL (exploitability — harness-dependent)
- Severity: Low (Medium only if a harness both keys invocation on `tool_input.skill` AND lets the model influence a top-level `skill`/`skill_name`/`name` field)
- Layers: 2 (hook + harness payload contract)
- Reachability: requires a harness payload containing attacker-influenceable duplicate skill fields; Claude Code's Skill payload carries only `tool_input.skill`, so the shipped-shape payload is safe.
- Evidence: evidence/K3-3-E9/summary.txt. Payload `{"skill":"short","tool_input":{"skill":"agent-guardrails"}}` → hook verifies `short` only, exit 0, regardless of JSON member order. Fail-open combination demonstrated: with agent-guardrails' installed SKILL.md tampered, the conflicting payload still yields `SKILL CONTENT VERIFIED 5/5 - installed skill=short` exit 0, while a single-field payload for the tampered skill is BLOCKED (`byte drift: SKILL.md`, exit 2). Unknown/renamed skills are BLOCKED (`unknown or unreadable skill`).
- Recommendation: when multiple containers/keys identify a skill, require all present values to agree (collect-then-compare) instead of first-match-wins.

### K3-3-C3 — Broken stderr pipe collapses an intended BLOCK (exit 2) into exit 120
- Verdict: CONFIRMED (behavior) / THEORETICAL (impact — depends on harness treating non-2 exits as non-blocking, which the hook's own comment says may happen)
- Severity: Low
- Layers: 1 (adapter error-path exit-code contract)
- Reachability: harness closes/breaks the hook's stderr pipe while the adapter is on a blocking path.
- Evidence: evidence/K3-3-E10/summary.txt. Tampered installed bytes + `2> >(exec true)` → exit **120** (the blocking `print(..., file=sys.stderr)` raises BrokenPipeError; the `except Exception` handler prints again to the broken pipe; interpreter exits 120). All other probes fail-closed at exit 2: malformed JSON, JSON array, empty stdin, >1 MiB stdin, missing installed root, unreadable installed file, closed stderr FD (`2>&-` still exits 2).
- Recommendation: wrap the handler's own stderr print in try/except and `os._exit(2)` (or write to `/dev/full`-safe fallback) so the blocking exit code survives dead stderr.

### K3-3-C4 — Direct (non-launcher) hook routing honors PYTHONPATH/sitecustomize shadowing
- Verdict: CONFIRMED (mechanic on unsupported routing) / THEORETICAL (requires attacker influence over the consumer's own environment)
- Severity: Low
- Layers: 1 (consumer runtime environment; documented routing is immune)
- Reachability: harness/operator invokes `python pretooluse-skill-integrity.py` directly with a hostile PYTHONPATH; e.g. a shadow `json.py` executes instead of stdlib before any verification (evidence: `PYTHONPATH=/tmp/K3-3/shadow` → `shadow-json-took-over`, marker file written, exit 1).
- Counter-evidence (HELD on supported paths): CWD `json.py` is NOT shadowed (script dir, not CWD, on sys.path); the launcher strips PYTHONPATH and runs `python -I -B` from the staged closure — launcher-driven hook with hostile PYTHONPATH set verified clean (exit 0, shadow not executed). evidence/K3-3-E4.
- Note: skills DO ship executable test/helper files (`test-block-dangerous-git.sh`, `test-scan-egress.sh`, `score.js`, etc.) to targets; they are signed, manifest-bound, and listed in the tree — disclosed, not smuggled.
- Recommendation: document that direct routing also requires a sanitized environment, or ship a `-I` wrapper; consider absolute-import guarding (`sys.path` hygiene) in the hook.

### K3-3-C5 — Forged handoff marker (objective 2 question: authority or defense-in-depth?)
- Verdict: FALSE-POSITIVE (it is (a) — defense-in-depth exactly as documented; never treated as authority)
- Severity: None
- Evidence: evidence/K3-3-E2. Marker format: env `IDC_SKILLS_FRESHNESS_HANDOFF` matched only against `sha256:[0-9a-f]{64}`. Forged `sha256:aaaa…` (64×`a`) runs `install.py` directly: install succeeds BUT the report shows the full signed 5-check integrity gate still executed (`integrity.authority: content-only`, all checks pass against the genuine signed manifest). Hook with forged marker + genuine installed bytes: `SKILL CONTENT VERIFIED 5/5` exit 0 — because every content check genuinely passed, not because the marker authorized anything. Without marker: BLOCKED exit 2. A forged marker against a tampered repo/installed bytes is still BLOCKED (see E9 controls).
- Conclusion: the marker is routing defense-in-depth; the trust root remains the pinned launcher + signed manifest/index. Matches install.py/reaccept.py/hook docstrings verbatim.

### K3-3-C6 — Parent/child overlap between two distinct targets is permitted
- Verdict: THEORETICAL
- Severity: Informational–Low
- Layers: 1 (consumer-chosen custom target topology)
- Reachability: consumer passes `--custom-target parent=/tmp/p --custom-target child=/tmp/p/inner`; both install "active" (evidence/K3-3-E5/overlap.txt). A clobber would additionally require a skill whose name equals the child path component (none exists in the registry), making this a self-inflicted-topology edge only.
- All hostile overlaps vs the CANONICAL tree are rejected (`unsafe target equals/inside/contains canonical skills directory`); equal or symlink-aliased targets dedupe to `covered`; custom names reject `..`, `/`, `.`, uppercase, reserved fleet names; TOCTOU destination-symlink swap after preflight is re-blocked at copy time (`refusing symlinked skill destination`, evidence/K3-3-E5b).
- Recommendation: optionally reject ancestor/descendant pairs among active targets for defense in depth.

## Coverage (objectives 1–11)

1. **Consumer arguments overriding verified root** — HELD. Launcher prefix-guard `--repo-r*` blocks all spelling/case/`=`/`--`-placement variants (E1: attempted `--repo-root /evil`, `--repo-root=/evil`, `-- --repo-root /evil`, `--repo-rOot` → FreshnessError). `--repo`/`--repository-root` evade the guard string but are rejected by downstream `allow_abbrev=False` parsers (`unrecognized arguments`, exit 2; evidence/K3-3-E1/install-argparse.txt). Duplicate `--repo-root` last-wins on the direct CLI is the consumer's own choice. Full-stack: `NOT READY`, no writes (E3).
2. **Forged handoff marker** — answered: (a) defense-in-depth as documented (C5, FALSE-POSITIVE). Forged marker works for routing but every content gate still enforces; tampered bytes remain BLOCKED.
3. **Live mutable consumer vs staged signed closure** — HELD. Launcher executes `staged_repo/scripts/*` (signed closure copied to a 0700 temp dir) under `python -I -B` with scrubbed env; live-tree tampering is detected before consumer start (`signed repository file drifted`, E3). Direct CLI use of the live tree remains same-user boundary (documented).
4. **Untracked module shadowing** — C4 (THEORETICAL, direct routing only); CWD shadowing HELD; launcher routing HELD (evidence). Shipped executable helpers are signed and disclosed. No namespace/package confusion found (`from . import skill_integrity` falls back to script-dir import only).
5. **Target overlap** — HELD for canonical-tree overlap/aliasing/traversal/reserved names/symlink destination/TOCTOU swap (E5, E5b); C6 (THEORETICAL) for parent/child between two custom targets. Case aliases: N/A on this ext4 filesystem (normcase handled; case-colliding paths inside skill dirs are rejected by `_assert_path_set_portable`).
6. **Preflight failure after earlier target changed** — CONFIRMED-as-documented: preflight catches shape errors run-wide before any write (shipped test + E5), but a mid-run I/O failure leaves earlier targets installed with NO rollback and NO residue (E6: exit 1, target `ok` kept both skills, zero `.install-*/.backup-*` leftovers). 2.0.3's docstring/help still states "not rollback-atomic after an unexpected I/O failure" — behavior matches the admission exactly.
7. **Mode/newline/sparse/hardlink/xattr/extra-file drift** — C1 CONFIRMED: installer compares bytes+symlinks+POSIX mode; hook compares sha256+size only; xattrs compared by neither. Newline/byte/extra-file drift: caught by both layers (E7/E9 controls). Sparse/hardlink: N/A — copies are materialized fresh by `copytree(copy2)`; in-flight hardlink mutation changes bytes → caught at next verification; `_file_record` double-stat catches mid-hash mutation.
8. **Installed-byte verification = claim vs closure** — HELD: `_sync_skill` recomputes the actual destination closure and compares it to BOTH the canonical source manifest and the signed manifest (staged and installed copies; "unchanged" path re-checks signed files too).
