## Candidates

### K3-2-C1 — Older-but-signed release is accepted whenever the external index authorizes it
- **Verdict: FALSE-POSITIVE (by design).** Severity: Informational.
- **Layer(s):** freshness authority semantics (1 layer).
- **Objective:** 1 (whole-tree replay of a valid signed older release).
- **Preconditions:** the *current* signed index lists the older release as its newest
  entry (i.e., the signing key holder published it) OR first run with the operator's
  `bootstrapIndexSHA256` pinning that older index.
- **Reachability/evidence:** `scen_g123.log` 1a: fixture repo re-released as a fully
  signed `2.0.2`, index seq 1 listing only 2.0.2, no checkpoint → `readyToRun=true`
  ("accepted"). This is not a bypass: the index *is* the freshness authority, and the
  launcher faithfully enforces exactly the newest signed entry. The anti-rollback teeth
  are the checkpoint: 1b — after a checkpoint at `indexSequence 2`, replaying the whole
  old world (repo at 2.0.2 + old signed index seq 1) →
  `FreshnessError: release index replayed a lower indexSequence`. Internal index
  rollback is impossible: 1c descending sequences → "strictly increasing"; 1d repo at
  older entry → "release tuple does not equal the newest signed index entry". Deleting
  the checkpoint (1e/1f-fixed) re-opens only the operator-pinned bootstrap digest —
  a *different* older index → "first-run index does not match the externally pinned
  bootstrap digest".
- **Why not a vuln:** forging this requires the signing key or write access to the
  externally protected config/checkpoint, both explicitly outside the boundary
  (launcher docstring lines 10–13; `integrity/README.md` "Honest scope").

### K3-2-C2 — `http.client.IncompleteRead` escapes fetch error handling (uncaught traceback)
- **Verdict: CONFIRMED (behavior observed; fail-closed).** Severity: Low (robustness;
  no boundary crossed).
- **Layer(s):** network fetch error handling (1 layer).
- **Objective:** 6 (partial reads / network failure mid-fetch).
- **Evidence:** `scen_g456.log` 6c5: a response whose `read()` raises
  `IncompleteRead` propagates out of `_fetch_https` — the except clause at
  `idc_verify_fresh.py:774` catches `(OSError, URLError, HTTPError)` but
  `http.client.HTTPException` is **not** an `OSError` subclass (verified MRO on
  Python 3.12.12). `main()` catches only `(FreshnessError, OSError, SubprocessError)`
  (line 1563), so a truncated TLS body yields an uncaught traceback, exit 1.
- **Impact:** availability/reporting only — no `READY` line, non-zero exit, checkpoint
  untouched. Truncated-but-"complete" bodies are still rejected by signature
  verification (5b). Remediation: add `http.client.HTTPException` to the except tuple.

### K3-2-C3 — Staged consumer snapshot is not re-hashed between content verification and consumer exec
- **Verdict: THEORETICAL.** Severity: Informational (hardening), per threat model.
- **Layer(s):** staged-execution (validate-then-run) gap (1 layer).
- **Objective:** 10 (snapshot A validated while snapshot B executes).
- **Evidence:** `scen_g7plus.log` 10b: a `content_runner` that mutates
  `staged/scripts/install.py` after returning lets the consumer execute the swapped
  bytes (`consumer executed staged installer containing: '# post-verify swap'`).
  Post-verify re-reads cover only live `manifest/verifier/launcher/config`
  (`idc_verify_fresh.py:1366–1387`), not the staged tree.
- **Reachability analysis:** the staged tree lives in a `0700` `TemporaryDirectory`;
  writing to it requires a same-UID process or a compromised *signed* verifier — both
  are explicitly outside the boundary ("not protection from an attacker who can replace
  the external launcher… or the OS-pinned Python runtime"; README: same-OS-user
  attackers excluded). Against the *declared* attacker (repository rollback / network
  attacker), 10c shows the consumer is immune to live-repo drift (it runs the staged
  signed bytes). Suggested hardening: re-hash staged files (or write-lock via
  `O_NOFOLLOW` fd-passing) immediately before `consumer_runner`.

### K3-2-C4 — Launcher process start under attacker environment without `-I` (PYTHONPATH pre-start injection)
- **Verdict: CONFIRMED, but explicitly the documented operator boundary.**
  Severity: Informational.
- **Layer(s):** process-start environment (1 layer).
- **Objective:** 12 (PYTHON*/loader vars).
- **Evidence:** `scen_g7plus.log` 12b: `PYTHONPATH=<evil>` + `python3 launcher --help`
  executes attacker `sitecustomize.py` (marker created); `python3 -I launcher` does not.
- **Boundary:** `integrity/README.md:151–158` mandates an external clean-environment
  wrapper invoking the pinned Python with `-I -B` and states loader variables "can
  execute before Python code starts; neither a digest check … nor `-I` can undo
  pre-start injection". All *children* of the launcher get a from-scratch environment
  (verified 11a and upstream `test_consumer_rejects_root_abbreviation_and_strips_hostile_environment`).
  Not a defect in the shipped bytes; flagged so operators treat the wrapper as mandatory.

### K3-2-C5 — Non-`FreshnessError` consumer exceptions escape `main()`'s catch list
- **Verdict: CONFIRMED (fail-closed).** Severity: Informational.
- **Layer(s):** consumer error handling (1 layer). **Objective:** 14.
- **Evidence:** `scen_g7plus.log` 14b: `consumer_runner` raising `RuntimeError`
  propagates uncaught (traceback, exit 1); the checkpoint has already advanced to the
  verified index. No readiness is printed; exit is non-zero. Matches README step 6:
  "A failed consumer does not roll the accepted freshness checkpoint backward"
  (14a: consumer exit 7 → `consumerExitCode=7`, checkpoint at seq 2 retained).

### K3-2-C6 — Redirect handler omits a fragment check on the redirect *target*
- **Verdict: FALSE-POSITIVE.** Severity: Informational.
- **Objective:** 6. **Evidence:** `supplementary-probes.log` 6b6-fixed: with a fresh
  handler, `https://allowed-host/x#frag` is accepted. Harmless: fragments are never
  transmitted to the server, and the post-fetch final-URL check
  (`idc_verify_fresh.py:762–770`) re-validates scheme/host/userinfo/port. Config URLs
  themselves reject fragments (6a3 HELD).

### K3-2-C7 — Split index/signature origins across two allowed hosts are accepted
- **Verdict: FALSE-POSITIVE (by design).** Severity: Informational.
- **Objective:** 6. **Evidence:** `scen_g456.log` 6a9: `indexURL` on `a.invalid`,
  `signatureURL` on `b.invalid`, both in `allowedHosts` → config accepted. The signature
  is verified over the exact fetched index bytes, so cross-origin substitution cannot
  forge content; worst case is fetch failure (fail-closed, 6d HELD).

### K3-2-C8 — Restoring an older checkpoint re-accepts a newer signed index
- **Verdict: FALSE-POSITIVE (by design).** Severity: Informational.
- **Objective:** 3. **Evidence:** `scen_g123.log` 3b1: checkpoint rolled back to seq 1,
  index seq 2 re-presented → accepted (this is the normal upgrade path). The rolled-back
  checkpoint cannot authorize anything older: 3b2 same-seq/different-digest →
  "equivocation"; 1b lower seq → "replayed a lower indexSequence"; 3c forward-crafted
  checkpoint only denies service (requires protected-state write access).

## Coverage (task §8.2 objectives 1–14)

1. **Whole-tree replay of older signed release** — C1 (FALSE-POSITIVE/by design);
   replay vs established checkpoint **HELD** (1b "replayed a lower indexSequence");
   internal single-index rollback **HELD** (1c/1d).
2. **Lower manifestSequence / indexSequence / truncation / reorder / removal /
   duplicates** — all **HELD**: 2a "release tuple", 2b "integer between 1 and …",
   2b2 "index floor", 2c1 "rewrote or removed accepted history", 2d/2e1 "strictly
   increasing", 2e2 "unique release names".
3. **Same-sequence equivocation; checkpoint rollback/forward** — equivocation **HELD**
   (3a, 3b2); checkpoint file format = canonical JSON
   `{schema,indexSequence,indexSHA256,releases}` at config `checkpointPath` under flock;
   roll-back → C8 (benign); roll-forward → DoS-only, needs protected-state write (3c);
   symlink/hardlink/dangling checkpoint **HELD** (3d1–3d3).
4. **Expiry/clock arithmetic** — **HELD**: expires==now reject, now+1 s accept,
   31 d exact accept / +1 s reject, generated now+300 s accept / +301 s reject,
   fractional-second and `+00:00` forms reject, validUntil==generatedAt reject;
   shipped index = exactly 30.0 days, accepted 1 s before expiry, expired at
   `validUntil`; last-second expiry before checkpoint write AND before consumer both
   reject (4m; upstream test corroborates).
5. **First-use bootstrap / TOCTOU double-fetch** — **HELD**: wrong bootstrap digest
   (5a, 1f-fixed); index/sig pair swapped between captures → "signature invalid" (5b);
   only the operator-pinned exact digest passes on first run (5c).
6. **HTTP/URL/origin tricks** — config layer **HELD** (6a1–6a8: http, userinfo,
   fragment, port≠443, unknown host, trailing dot, uppercase hosts, maxRedirects>3);
   redirect handler **HELD** (6b1–6b5); fragment-on-target C6 (cosmetic); split origins
   C7 (by design); oversize body **HELD** (6c2); connection refused / proxy env
   **HELD** (6d/6e, `ProxyHandler({})`); partial read → C2 (fail-closed traceback).
   Live-TLS mock on 443 **UNVERIFIED** (uid 999; logic covered at handler layer).
7. **Path-identity attacks** — **HELD**: config symlink/hardlink (7a/7b), launcher via
   parent symlink into repo (7c), checkpoint parent symlink (7d), index source symlink
   (7f); repo_root via symlink resolves and verifies (7e, correct). Bind-mount alias
   **UNVERIFIED** (no mount privileges) — `_path_is_within` walks
   `os.path.samefile` per ancestor (inode-based), which is exactly the mount-alias
   case (`idc_verify_fresh.py:144–160`). Case-fold: upstream case-alias test passes;
   Linux/ext4 here.
8. **Installed launcher bytes vs signed source; first-fetch trust order** — **HELD**:
   8a "captured freshness launcher differs", 8b "release tuple"; trust order mapped
   (blind log §1): first fetch is authenticated only by the pinned-key signature;
   launcher bytes are bound by the manifest record AND the index pin; the launcher
   cannot be tricked into trusting a fetched copy of itself.
9. **Captured verifier vs manifest/index/git pins** — **HELD**: 9a reject before
   content execution (content runner never invoked), 9b "release tuple"; git-tree blob
   sha1 recomputed per file (upstream mode/blob-drift tests pass).
10. **Validate-then-run gap** — consumer executes the staged signed snapshot; live
    mutation during verification **HELD** (10a, 10c); staged snapshot itself not
    re-hashed before consumer exec → C3 (THEORETICAL, out of declared threat model).
11. **.git/config/hooks/filters/fsmonitor/submodules/gitdir/GIT_* env** — **HELD**:

    from scratch (supplementary probe, 191 paths inventoried, hook not fired).
12. **Executable path/hash, PATH shadowing, shebang, env, loader vars, temp dirs** —
    **HELD** for all children (from-scratch env, pinned digest-verified executables,
    `os.defpath` resolution, random 0700 temp dirs); launcher *process start* under
    hostile env → C4 (documented operator-wrapper requirement, `-I` suppresses).
13. **Consumer execution when offline/unverified/expired/red** — **HELD**, nothing
    fails open: offline verify → `readyToRun=false`, `freshness=UNVERIFIED`, exit 3

    *containing* the field is rejected ("improperly emitted", upstream test).
14. **Checkpoint advancement/rollback on consumer failure** — **HELD/by design**:
    checkpoint advances only after content+freshness pass and is retained on consumer
    failure (14a, README-mandated); unexpected consumer exceptions fail closed with
    non-zero exit (14b → C5).

## Bottom line

No CONFIRMED vulnerability crosses the signed/freshness boundary. Every replay,
rollback, equivocation, truncation, expiry, path-identity, git-hardening, and
fail-open attempt was rejected at the predicted gate. Findings: two informational
robustness nits (C2, C5 — uncaught non-OSError exceptions, still fail-closed), one
theoretical defense-in-depth gap (C3 — staged snapshot not re-hashed before consumer,
exploitable only by same-UID/compromised-verifier actors outside the declared model),
and four by-design/false-positive clarifications (C1, C6, C7, C8). C4 restates the
documented mandatory clean-environment wrapper.
