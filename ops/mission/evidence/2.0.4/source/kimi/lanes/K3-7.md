## Blind pass log (hypotheses before reading docs)

Formed after anchor verification, before reading README/integrity/README/release prose:

- H1: A `core.autocrlf=true` checkout will CRLF-mangle text files and the verifier will fail closed (hash mismatch) — or worse, silently pass if hashing is newline-insensitive. (Before noticing `.gitattributes`.)
- H2: The Windows mode story is a signed external override table — I expected a separate signed file; if instead the modes are simply skipped on Windows, that is a fail-open on a documented platform.
- H3: There will be no explicit `sys.version_info` guard; the "Xcode 3.9 failed closed" note implies an incidental AttributeError somewhere in `pathlib` (guessed `Path.walk`, 3.12+).
- H4: ssh-keygen will be located via bare-name PATH execvp in at least one tool (asymmetric with the launcher's pinned runtimes) — a contentReady-spoofing surface, but not a readyToRun one.
- H5: `_assert_path_set_portable` will check case and NFC collisions but a crafted manifest with drive-letter/backslash paths might alias silently on Linux (backslash is a literal filename character there).
- H6: The release-page "5/5+freshness / readyToRun=true on public clones" claim will be reproducible end-to-end only if the launcher's external-install ceremony can be satisfied in /tmp; expected at least one config-format stumble (canonical JSON).
- H7: CHANGELOG/tag will still carry "candidate" wording contradicting the GitHub release.
- H8: At least one bash-4-only construct will turn up in the "300/300 on bash 3.2" fixture matrices (prior: low; the scripts are security-reviewed).

Outcomes: H1 wrong (gitattributes `eol=lf` makes autocrlf moot — and good), H2 wrong (overrides come from inside the signed manifest, gated on os.name=="nt"), H3 half-right (no guard; breaking APIs are 3.10 additions `Path.stat(follow_symlinks=)` and `Path.write_text(newline=)`, not `Path.walk`), H4 confirmed, H5 wrong (set-diff closes it), H6 confirmed (canonical-JSON stumble, then full pass), H7 confirmed (acknowledged in release body), H8 wrong (no bash-4 constructs found).

## Candidates (§9 fields)

### K3-7-C1 — Dangerous-git guard fails OPEN when python3/jq/payload is missing or malformed

- **Verdict:** CONFIRMED (static + code cite; behavior is the documented design)
- **Severity:** Low
- **Platform:** all (POSIX execution observed only via fixture matrix; the fail-open branch itself read statically)
- **Where:** `skills/agent-guardrails/scripts/block-dangerous-git.sh:79-90` — empty/unparseable payload → `exit 0` ("guard OPEN"); `command -v python3` absent → `exit 0`; header comment: malformed payload / missing interpreters "→ guard OPENS (announces it, allows), by design, so a parse error cannot wedge every command"; "never [wire it] as the only barrier". Classifier "self-guards EVERY internal error into a fail-OPEN (exit 0 + note)".
- **Evidence:** evidence/K3-7-bash/guard-failopen.txt
- **Assessment:** Documented, announced (stderr), advisory-by-design layer sitting *beneath* the signed content gate; CHANGELOG 2.0.3 explicitly retains "the Git string classifier remains advisory beneath OS/repository controls". Task severity floor says a documented-platform fail-open = Medium; I rate Low because the fail-open is the specified contract of an explicitly non-authoritative advisory guard (not a portability gap, and not part of the signed closure's authorization decision). Flagging for lead adjudication.
- **Recommendation:** none required for this release; optionally have the guard exit 2 when `IDC_GUARD_STRICT=1` is set for harnesses that can tolerate wedging.

### K3-7-C2 — In-tree verifier resolves `ssh-keygen` via inherited PATH, asymmetric with the pinned launcher

- **Verdict:** CONFIRMED (static)
- **Severity:** Low
- **Platform:** all POSIX (Linux observed); Windows UNVERIFIED ON Windows (missing Windows + OpenSSH-for-Windows)
- **Where:** `scripts/skill_integrity.py:797` (`["ssh-keygen","-lf","-"]`), `:915` (`-Y verify`), `:1369` (`-Y sign`) — bare-name `subprocess.run`, i.e. caller PATH. Contrast: git discovery in the same file uses `shutil.which("git", path=os.defpath)` (`:630`), and the launcher's `_trusted_executable` (bootstrap/idc_verify_fresh.py:207-215) uses `os.defpath` + strict resolve + regular-file check, with the release config additionally pinning sha256 digests of python/git/ssh-keygen (`parse_config`, `:601-647`).
- **Consequence:** a PATH-poisoned `ssh-keygen` could make the **in-tree** verifier emit `contentReady=true` for a forged manifest. It cannot produce `readyToRun=true`: the launcher re-verifies with the digest-pinned binary and refuses to treat `contentReady` as authority (it hard-fails if the in-tree report ever contains a `readyToRun` key — idc_verify_fresh.py:1164-1165, verified in code).
- **Mitigation documented:** the verifier's own docstring states "Code inside an untrusted repository cannot establish its own root of trust"; README restates it.
- **Recommendation (non-blocking):** switch the three in-tree invocations to `shutil.which("ssh-keygen", path=os.defpath)` for symmetry; zero cost.

### K3-7-C3 — Minimum-Python contract is implicit; 3.9 fails closed via incidental TypeError, not a guard

- **Verdict:** CONFIRMED on Linux cpython 3.9.25 (executed)
- **Severity:** Low (fail-closed direction; unclear error message; undocumented minimum)
- **Platform:** Linux (3.9.25/3.12.12 executed); same APIs missing on any 3.9 regardless of OS
- **Where (the two post-3.9 APIs):**
  - `scripts/install.py:287` — `path.stat(follow_symlinks=False)` (`Path.stat(follow_symlinks=)` added in **Python 3.10**)
  - `scripts/install.py:1174` and `bootstrap/idc_verify_fresh.py:250` — `Path.write_text(..., newline=...)` (`newline=` added in **Python 3.10**)
- **Measured:** full suite under 3.9.25: `FAILED (failures=1, errors=32)` of 101; every distinct error is `TypeError: stat() got an unexpected keyword argument 'follow_symlinks'` (×13) or `TypeError: write_text() got an unexpected keyword argument 'newline'` (×20). Under 3.12.12: **101/101 OK**. Notably the in-tree `skill_integrity.py verify` alone **passes 5/5 on 3.9.25** — the 3.9 break is in installer + launcher paths. Evidence: evidence/K3-7-python39/summary.txt
- **Contract check:** no `sys.version_info` guard exists in any of the three tools; README/integrity README state no minimum Python; CI pins 3.12 on ubuntu/windows/macos (`.github/workflows/validate.yml:33-37`). Failure mode on 3.9 is a raw traceback (non-zero exit, no pass emitted) — fail-closed but with an opaque message.
- **Recommendation:** one-line guard (`if sys.version_info < (3, 10): sys.exit("idc-skills requires Python ≥ 3.10 (CI-tested 3.12)")`) plus a README line. Not a security defect.

### K3-7-C7 — Windows mode/ownership checks are design-limited (carry-forward + POSIX-only owner checks)

- **Verdict:** THEORETICAL (static); UNVERIFIED ON Windows — missing dependency: Windows/NTFS host (none available)
- **Severity:** Low
- **Where:** `scripts/skill_integrity.py:609-612` — on `os.name == "nt"`, `posixMode` is taken from the **signed manifest's own `repositoryFiles` records** (the "override table" is internal to the signed closure, not an external file — verify path at `:1111-1116` and `:1234-1239` passes `stored.get("repositoryFiles")` only when `os.name == "nt"`). Docstring at `:544-549` states the design: "authenticated manifest modes are therefore carried forward while bytes are independently recomputed; the external launcher restores those signed modes in its private execution snapshot." Launcher's owner/writability checks are POSIX-gated (`os.name != "nt"`, idc_verify_fresh.py:573-575, 599-601, 1213-1219).
- **Assessment:** bytes remain hash-pinned on Windows (a swapped executable still fails digest), so this is not a fail-open; the unmeasured surface is mode/ACL metadata, and integrity/README.md:166-169 discloses that stronger claims require "Windows ACL enforcement". Gate is inert off-Windows: exercised on Linux — an override `posixMode=0` against a real 0o755 file is ignored (evidence/K3-7-paths/results.txt).
- **Coordinator cross-check:** filemode=false + correct index modes still checks out 0o755 on disk (git writes exec bits at checkout regardless of core.filemode) → verifier **passes 5/5** (measured). Forcing the 21 executables to 0644 (what a non-filemode environment would produce) → **fails closed 4/5** (`local_bytes: repositoryFiles differs from the signed manifest`) (evidence/K3-7-filemode/nofm2.json). The launcher's hardened git invocation forces `-c core.filemode=true` (idc_verify_fresh.py:989-992), so the authoritative path enforces modes itself; the consumer-facing docs never state a filemode/autocrlf requirement for the bare in-tree verifier path — minor doc gap, fail-closed consequence.

### K3-7-C8 — `os.defpath`-restricted ssh-keygen lookup likely unsatisfiable on stock Windows

- **Verdict:** THEORETICAL (static); UNVERIFIED ON Windows — missing dependency: Windows host (none available)
- **Severity:** Low (fail-CLOSED/availability only)
- **Where:** `bootstrap/idc_verify_fresh.py:207-215` uses `shutil.which(name, path=os.defpath)`; on Windows `os.defpath` is `.;C:\bin`, which does not include `C:\Windows\System32\OpenSSH` where Microsoft ships ssh-keygen. The freshness config's `executables.sshKeygen` record (absolute path + sha256) bypasses discovery entirely, so a correct deployment is unaffected; ad-hoc fallback discovery would fail closed with "trusted system executable is unavailable".
- **Recommendation:** none for security; document that Windows deployments must pin `executables.sshKeygen`.
