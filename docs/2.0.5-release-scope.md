# IDC Skills Forge 2.0.5 release scope

Version 2.0.5 is a stable **limited-trust, public content-authenticated release**. It gives Forge 50 an evidence-routed public front door without claiming that a documentation and identity layer activates the stronger production threshold/freshness ceremony. The two assurance profiles remain distinct.

## What changed from 2.0.4

- The public README now opens with the owner-selected H1 “Welded Constellation” treatment, the entrance “Velocity, welded to proof,” and five outcome routes: Build, Research, Operate, Verify & Ship, and Architect.
- A deterministic catalog exposes all 50 registered islands in canonical build order and names 25 unique editorial starting points. Routes are recommendations, not popularity rankings or blanket certifications.
- Safe acquisition, verification, contribution, and vulnerability-reporting guides make the authority boundary visible before installation.
- Front-door tests bind the selected local asset, catalog generation, local public links, heading structure, route membership, and exact release-line metadata.
- The registry advances to release `2.0.5` and `manifestSequence` 3. Every versioned witness and release asset is regenerated for the new tracked tree.

No skill body, installer, guard, egress scanner, threshold-root implementation, freshness launcher, or release verifier changed. No immutable 2.0.4 tag, manifest, signature, witness, release asset, or evidence receipt is modified or reused as 2.0.5 evidence.

## What 2.0.5 claims

- The release manifest binds the exact tracked release bytes and POSIX mode intent for all 50 skills and the declared control-file closure.
- The owner-held Forge content key signs those canonical manifest bytes. The private key remains in 1Password and is never committed, copied into an environment variable, or written into release evidence.
- A first-contact consumer can compare the full Forge signing fingerprint and immutable 2.0.5 identity against two version-specific out-of-repository publications before using an independently selected OpenSSH executable to verify the manifest.
- The published Git tag, commit, tree, manifest, signature, and release assets must agree, and the accepted tree must reproduce from a clean clone.
- Repository tests, the Git-grammar corpus, the egress corpus, sealed-browser checks, Forge-50 closure, front-door checks, and protected GitHub CI must be green for their stated scopes at the released tree.
- Fresh independent acceptance is bound to the exact 2.0.5 commit and tree and becomes void if either moves.

The company-site JSON witness and DNSSEC TXT record must show the same release tag, commit, tree, manifest SHA-256, and full signing fingerprint. The detached-signature digest is additionally compared between the GitHub release asset and company-site JSON; the DNS TXT schema does not carry it. GitHub remains the only canonical source tree. The tracked README is navigation, not a self-issued identity root.

## What 2.0.5 does not claim

- production 2-of-3 root or release-role custody;
- multi-party signer withholding or root-rotation resilience in live custody;
- a completed eleven-lane Kimi K3-204 acceptance packet;
- independent Windows/NTFS/OpenSSH platform acceptance;
- freshness-authorized four-root fleet parity;
- a disjoint publication-observer attestation;
- universal successful behavior across every documented harness surface; or
- the full external-threshold result `readyToRun=true`.

The threshold-root, release-statement, freshness, review, platform, fleet, and publication-observer machinery remains implemented and tested source. Its production activation is a separate mission and must receive another immutable version identity when completed.

The unchanged `scripts/verify_public_release.py` gate belongs to the stronger full-profile ceremony and retains its 2.0.4-pinned construction contract. It is not a scoped 2.0.5 promotion gate, and this release must not report that tool's `PUBLIC RELEASE VERIFIED` result. Post-publication comparison of GitHub with the two 2.0.5 witnesses is narrower evidence under this document, not a substitute label for the stronger verifier.

## Promotion gates

Before the `2.0.5` tag is published:

1. finalize and stage only the approved front-door and release-control inventory;
2. run author QA, full repository tests, security matrices, asset inspection, and clean-scope checks;
3. regenerate and owner-sign the canonical manifest as the last tracked-byte mutation;
4. commit and reproduce the exact candidate from a clean detached clone;
5. obtain protected CI and fresh independent exact-head acceptance without changing the accepted tree;
6. publish new 2.0.5 HTTPS and DNSSEC witnesses without altering the 2.0.4 records; and
7. publish the immutable annotated tag and exact release assets, then re-read GitHub and both external channels and compare every bound value.

Any mismatch stops promotion. A green result establishes only its stated authority; it never silently upgrades this release to the deferred full-freshness profile.
