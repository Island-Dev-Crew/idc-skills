# IDC Skills Forge 2.0.4 release scope

Version 2.0.4 is a stable **limited-trust, public content-authenticated
release**. It is not
the production threshold-accepted release described by the complete G0-G6
ceremony. These are different assurance profiles, and no passing result in the
first profile is evidence that the second profile passed.

## What 2.0.4 claims

- The release manifest binds the exact tracked release bytes and POSIX mode
  intent for all 50 skills and the declared control-file closure.
- The owner-held Forge content key signs those canonical manifest bytes. The
  private key remains in 1Password and is never committed, copied into an
  environment variable, or written into release evidence.
- A first-contact consumer can compare the full Forge signing fingerprint and
  immutable release identity against two out-of-repository publications before
  using an independently selected OpenSSH executable to verify the manifest.
- The published Git tag, commit, tree, manifest, and release assets must agree,
  and the accepted tree must reproduce from a clean clone.
- Repository tests, the Git-grammar corpus, the egress corpus, the sealed
  browser checks, Forge-50 closure, and protected GitHub CI must be green for
  their stated scopes at the released tree.
- Claude independently reproduced the repaired construction controls, and the
  available Kimi K3 lanes supplied adversarial findings that were repaired and
  regression-tested. The incomplete Kimi engagement is described as partial,
  never as final acceptance.

The two external publications must show the same full signing fingerprint,
release tag, commit, tree, and manifest SHA-256. One is the company-controlled
well-known endpoint; the second is a DNSSEC or independently administered
transparency channel. GitHub remains the only canonical source tree.

## What 2.0.4 does not claim

- production 2-of-3 root or release-role custody;
- multi-party signer withholding or root-rotation resilience in live custody;
- a completed eleven-lane Kimi K3-204 acceptance packet;
- independent Windows/NTFS/OpenSSH platform acceptance;
- freshness-authorized four-root fleet parity;
- a disjoint publication-observer attestation; or
- the full external-threshold result `readyToRun=true`.

The current `verify_public_release.py` gate also requires a threshold release
statement and a separate, disjoint publication-observer signature. Because the
2.0.4 profile does not claim those authorities, it must not report that gate's
`PUBLIC RELEASE VERIFIED` result. Post-publication comparison of GitHub and the
two witnesses is scoped evidence, not a substitute label for that stronger
verifier.

The threshold-root, release-statement, freshness, review, platform, fleet, and
publication-observer machinery ships as implemented and tested source. Its
production activation remains an open mission. Because a published tag is
immutable, later completion of that stronger ceremony receives a new version
identity rather than rewriting 2.0.4.

## Promotion gates for the scoped public release

Before the `2.0.4` tag is made public:

1. finalize and stage the intended Git inventory;
2. regenerate and owner-sign the canonical manifest as the last tracked-byte
   mutation;
3. commit and clean-clone replay the exact candidate;
4. obtain protected CI and review without changing the accepted tree;
5. publish the full fingerprint and candidate identity through both external
   channels; and
6. publish the immutable tag and exact release assets, then independently
   re-read GitHub and both channels and compare every bound value.

Any mismatch stops promotion. This scoped release is useful precisely because
its narrower claims are inspectable; it must never borrow a stronger label from
an unperformed ceremony.
